# ADR-001：自研办公空间设计平台

- 日期：2026-10-03
- 状态：已采纳，分阶段实施
- 适用范围：本仓库的办公空间规划、家具配置、报价与 BIM 交付产品
- 取代的决策：[酷家乐集成研究与 MVP 实施方案](./酷家乐集成研究与MVP实施方案.md)第 1、2、6、12、16 节关于将酷家乐作为核心能力层的实施决定。原文保留为调研记录，不再作为当前开发依据。

## 1. 背景与判断

产品目标是把客户的办公场地与人员需求转换为可编辑、可报价、可交付的家具方案。自有办公家具需要建立尺寸、组合、价格、二维符号、三维模型和 Revit 族数据；这些资产也是自动排布与采购交付的基础。将其维护在第三方设计平台内，会额外增加模型映射和数据同步工作。

仓库目前有两种成熟度不同的实现：

- `layout.html`、`scheme.js`、`models/base.json` 和 `schemes/` 面向 4F 项目，包含较深入的候选排布、校核及方案推导，但依赖该项目的底板和数据形状。
- `studio.html`、`studio.js` 是通用产品原型，已有场地标注、家具编辑和 A/B/C 初稿；布局规则较简化，项目保存在浏览器 `localStorage`。
- `api/generate.js` 等接口服务现有图像产出；效果图不是可编辑场景的事实来源。

因此，首要工作是统一数据协议并抽取可复用的排布与校核能力，再逐步完善编辑、模型与交付。不能以 4F 项目的成功案例代替跨项目验证。

## 2. 决策

建设自有办公空间设计平台。核心场景数据、办公家具目录、布局与校核规则、方案版本、BOM 与报价由本系统管理。Web 编辑器、三维预览和 Revit 连接器读写同一套已版本化的数据协议。不以酷家乐 API、账号、编辑器、模型库或渲染结果作为核心工作流的依赖。

可采用有明确许可和维护来源的基础组件，例如 Web 图形库、DXF 解析库、三维引擎、数据库和后台渲染器。这里的“自研”指自有产品逻辑、数据和交付链路，不要求重写文件格式解析器或光线追踪器。

### 产品主链路

```text
尺寸 / DXF / PDF或图片底图 / Revit 场地
  → 场地核对与确认
  → 办公需求 + 自有家具目录
  → 多候选布局与校核
  → A/B/C 可编辑方案
  → 2D / 3D 预览、BOM 与报价
  → Revit 落模及项目交付
```

所有导入结果在生成正式方案前须由用户确认比例、边界、入口、出口、柱和保留区域。算法检查输出具体问题和位置；消防、无障碍与施工合规结论仍由有资质的专业人员复核。

## 3. 第一版边界

首版支持单层办公空间、经过认证的自有办公家具，以及工位、会议、电话亭、储物等常见配置。用户可以编辑场地，填写人数和配套需求，得到容量、均衡、舒适三种取向的方案，手动调整并导出 BOM、报价与 Revit 布置。

输入优先级：

1. 尺寸建场地、手动绘制与现有结构化场地数据。
2. DXF 的可识别图层与几何导入，导入后人工确认。
3. PDF、JPG、PNG 作为底图，经过已知尺寸校准和人工描线。
4. Revit 插件读取指定楼层的相关构件并生成场地草稿，人工确认后使用。

首版不承诺任意 DWG 或扫描图自动识别、任意第三方家具即插即用、实时双向 Revit 同步、照片级云渲染或自动生成施工级合规文件。这些能力在主链路通过真实项目验证后单独立项。

## 4. 数据与模块边界

四类核心数据独立版本化：

| 数据 | 主要内容 | 维护者 |
| --- | --- | --- |
| `site` | 楼层、边界、墙、门窗、柱、禁占区、入口与出口、坐标变换、来源及确认版本 | 场地编辑器与导入适配器 |
| `brief` | 人数、部门与功能需求、通道目标、预算、偏好、使用的规则集版本 | 需求界面 |
| `catalog` | 产品与部件 SKU、可选尺寸和组合、净空、价格、二维符号、GLB、Revit 族映射 | 自有家具目录 |
| `layout` | 所用 `site`/`brief`/`catalog` 版本、房间与家具实例、方案取向、检查结果、算法版本与种子 | 布局引擎及方案编辑器 |

具体 JSON Schema 在实施阶段单独发布为 `v1`；以上是必须保持的对象边界，不把现有 4F JSON 直接宣布为通用协议。所有对象有稳定 ID；家具实例引用已发布的目录版本，历史方案不因产品改价或模型替换而静默变化。

内部长度统一为毫米。每个场地记录本地原点、轴向和到外部模型的显式变换；Revit 单位转换仅在连接器边界执行。坐标和旋转的含义必须写入协议并以往返测试验证。二维图形、三维网格、图片和清单都是结构化场景的派生结果。

每次正式场地确认和方案保存产生可追溯版本。场地修改后，旧方案标记为过期；重新生成创建新版本，不覆盖已交付版本。浏览器缓存只用于编辑草稿和离线恢复，不能作为跨设备项目记录。

### 目标代码边界

```text
scene-schema       数据类型、校验、迁移、单位与坐标协议
geometry-core      房间拓扑、碰撞、净空与空间索引
layout-core        候选生成、规则检查、评分与可解释结果
catalog-core       家具组合、SKU、版本、BOM 与报价计算
web-editor         场地编辑、方案比较、二维与三维预览
project-api        项目、版本、文件及后台任务
import-workers     DXF 与底图处理
revit-connector    Revit 场地导出、族映射、预览与方案应用
```

这些是代码职责，不要求首日建立八个服务。先在一个仓库内按模块拆分；出现真实的部署或扩容需要时再拆进程。

## 5. 技术选型

- 共享场景与布局核心：TypeScript、JSON Schema；算法保持与浏览器 DOM 和服务端运行环境解耦。新规则使用可重复的输入、随机种子与版本号。
- Web：现有页面继续承担回归和演示；新编辑器逐步采用 React + TypeScript。二维画布和三维预览分别选用成熟的 Canvas 图形库与 Three.js，均只修改或展示共享场景对象。
- 服务端：Node.js + TypeScript；多用户与跨设备保存启用 PostgreSQL，场景和方案保存不可变版本，大文件进入对象存储。后台任务只在导入或渲染实际需要时加入。
- 图纸输入：DXF 采用独立解析工作流；PDF 和图片先作为可校准底图。DWG 读取需要另行评估合法授权的解析 SDK、可支持版本、成本和样本质量，不能以文件扩展名推断可用性。
- 3D 与渲染：GLB/glTF 作为 Web 模型交付格式；浏览器提供即时预览。照片级渲染可在后续以独立后台任务接入 Blender，不影响场景协议。
- Revit：C# 插件按实际客户使用的大版本分别构建。插件执行单位和坐标转换、族映射、模型读写与事务；布局计算由共享核心或服务端负责。应用方案前提供预览和差异，自动元素带稳定实例 ID，人工元素不参与自动清理。
- AI：把自然语言转换成经过校验的 `brief`、发起已有工具操作和解释结果。精确几何、BOM 和检查结论由确定性代码计算。

以上是目标技术栈。现有代码迁移期间允许新旧页面并存，且不为了采用框架而重写已验证的 4F 逻辑。

## 6. 实施与验收门槛

### M1：协议与跨项目样本

发布 `site/brief/catalog/layout v1`，提供从 `models/base.json`、`schemes/*.json` 和 `studio.js` 项目 JSON 到新协议的转换器。保留 4F 作为历史回归样本，另准备数个模拟矩形办公场地，覆盖不同面积、门窗、柱、禁占区和出入口位置。检查对象 ID、数量、尺寸、坐标和导入导出往返结果。

通过门槛：同一份方案在二维视图、家具清单和 JSON 导出中的实例数、位置及产品代码一致；历史原始文件保持可读。

### M2：排布与校核内核

抽取 4F 页中的房间装箱、工位排布、评分及连通性检查，识别并移除项目固定坐标。将通用原型的简化生成器改为调用共享内核。检查结果区分硬约束、偏好评分和需人工复核事项。

通过门槛：4F 与各模拟矩形样本均可生成多种可解释候选；相同输入、目录版本、规则版本和种子得到相同输出；不满足人数或空间要求时明确报告缺口。

### M3：编辑与项目记录

完善场地编辑、家具微调、撤销/重做、场地确认和版本恢复。建立项目 API 与持久化，迁移 `localStorage` 中已有的可导出项目。场地改变时标记方案过期。

通过门槛：保存、刷新、跨设备打开、回退版本后场景一致；对同一方案的修改不会悄悄改变旧版本。

### M4：真实家具与交付

为一套在售办公家具建立尺寸、组合、净空、SKU、价格、2D 符号、轻量 GLB 和 Revit 族映射。实现三维预览、BOM/报价及 Revit 导入闭环。

通过门槛：至少两个非 4F 的模拟矩形项目从场地输入走到报价和 Revit 落模；同一方案重复导入无重复实例，失败操作可整体撤销，人工移动或增加的元素在再次应用前得到差异提示。

只有 M1 与 M2 的跨项目门槛通过，才把自动布局对外描述为“通用办公空间排布”。

## 7. 代价、风险与后续决定

本决策获得自有场景、家具与报价数据的控制权，同时需要自行维护编辑器、家具资产质量、图纸兼容和 Revit 版本。最大早期风险是把 4F 中隐含的坐标、采光、疏散口与固定房间假设带进通用算法。通过迁移样本、规则版本和跨项目回归控制此风险。

仍需在相应阶段作出具体决定：首批支持的 Revit 版本、正式采用的 DXF/DWG 解析组件及许可、首批家具系列、报价税费/安装规则、多人同时编辑方式以及照片级渲染服务等级。这些决定不阻塞 M1 的数据协议和样本迁移。

## 8. MVP 业务能力设计（规划，尚未实施）

当前仍处于 MVP 阶段。本节记录产品要验证的业务能力与边界，不表示这些能力已经存在，也不授权立即开发。M1–M4 是后续实施路线；MVP 的场地验证使用模拟矩形样本，不以取得真实房源为前提。

产品面向办公家具销售与项目交付。客户体验是一条连续流程：建立项目、确认场地、填写办公需求、比较方案、修改方案、核对家具与报价、分享或交付。内部能力按业务对象划分，使方案修改后能明确哪些结果需要更新。

| 业务能力 | 负责的决定与规则 | MVP 阶段要验证的产出 |
| --- | --- | --- |
| 项目与版本 | 客户、场地、参与人、当前方案及确认记录属于哪个项目 | 可追溯的项目与方案版本；先允许设计师辅助操作 |
| 场地管理 | 面积、墙、门窗、柱、入口及禁占区是否可信 | 经人工核对的场地；输入可先用尺寸或人工描线 |
| 需求管理 | 人数、工作方式、会议与配套、预算及优先级是什么 | 一份可修改、可回溯的办公需求 |
| 自有产品配置 | 哪些家具与部件可组合，尺寸、净空、SKU 和价格是什么 | 一套真实在售家具的受控配置目录 |
| 方案生成与编辑 | 家具与功能区怎样布置，容量、舒适度和预算如何取舍 | 多个可解释、可人工调整的候选方案 |
| 方案校核 | 哪些需求未满足，哪里有碰撞、通道或出入口问题 | 与方案对象关联的问题清单，标明需人工复核项 |
| BOM 与报价 | 选定方案需要哪些产品，数量、费用和报价依据是什么 | 由真实 SKU 计算的清单与报价版本；占位价格不能作为客户正式报价 |
| 展示与交付 | 客户和设计师如何查看、确认并继续使用方案 | 可分享的方案视图；Revit 与安装资料按 M4 接入 |

### 业务对象与变更关系

MVP 先约定 `项目、场地、需求、产品配置、方案` 五类对象及其版本关系。方案引用确定的场地、需求、目录和规则版本；校核、BOM、报价、2D/3D 展示从该方案推导。效果图仅用于展示，不能反向决定家具数量、尺寸或报价。

当客户改变人数或会议需求时，创建新的需求版本并生成或编辑新方案；校核、BOM 与报价随新方案重算。场地变更使依赖旧场地的方案标记为待复核。目录改价不静默覆盖已经发给客户的报价。客户确认的是某个明确的方案与报价版本，交付端使用同一版本。

### MVP 验证顺序

1. 用 4F 作历史回归，并创建至少三个模拟矩形办公场地：小型无柱、中型带柱、大型带禁占区；改变门窗和出口位置，验证场地、需求和方案对象以及排布边界。样本尺寸、障碍与预期结果记录在 [MVP 模拟场地与验收](./MVP-模拟场地验收.md)，便于重复测试。
2. 选一套真实在售家具验证配置、排布、BOM 和报价能否对上；在此之前只把当前报价页视作流程演示。
3. 让设计师和试用者使用这些模拟场地，完整走过确认场地、比较和修改方案、核对报价的流程，记录每一步需要的人工补救。
4. 通过上述功能验证后，再确定自助导图、Revit、渲染和更细的交付能力何时进入 MVP 后续迭代。模拟场地只能证明流程与规则在已覆盖的几何条件下可用；真实项目交付前另做现场数据、产品配置和专业校核验证。

这份能力划分用于设计产品与验收试点，不要求为每项能力单独建立页面、仓库或服务。

从三个模拟场地扩展到批量房源的条件、数据契约和验收路线，见[办公房源初筛扩容方案](./房源初筛扩容方案.md)。该方案尚未实施，不改变当前 MVP 范围。
