# 办公房源初筛扩容方案

状态：规划，尚未实现。适用范围是从当前三个模拟矩形场地，逐步扩展到数十至约一千套可比较的办公房源。本方案延续 [ADR-001](./ADR-001-自研办公空间设计平台.md) 的自有场景与布局内核决策；不改变当前 MVP 的交付范围。

## 当前能力与扩容目标

当前 `broker.js` 为三个固定场地各生成四种空间骨架，按启发式分数排序，取第一名计算需求缺口，并在卡片中展示摘要。打开场地后再展示 A/B/C 三版及逐项评估。三个场地使用同一份需求；额外空间、部门、关系和取舍中尚未自动校核的部分继续标为 `Not assessed`。现有计算同步运行在浏览器主线程，项目主要保存在 `localStorage`。这是一条可演示的概念初筛流程，不是大房源库搜索，也不能证明法规、通行或施工可行性。

扩容目标是让用户先检索房源，再看到可解释的候选名单，最后只对值得深入比较的房源运行完整排布。不能把当前循环从三个场地直接扩大到一千个：一千套各生成四个候选意味着约四千次同步生成，还缺少房源持久化、数据质量、任务取消和结果版本管理。

## 扩容时保持不变的用户语义

需求输入仍归一为一份 `brief`。自然语言、手工编辑和以后新增的模板都只是输入适配器；不得由输入方式决定不同的排布规则。每个房源的结果须区分：

| 层级 | 可展示状态 | 含义 |
| --- | --- | --- |
| 房源检索 | 已排除、资料不足、待详细计算、已有概念评估 | 检索状态，不等于布局结论 |
| 单条需求 | 概念已放置、数量缺口、需要确认、尚未评估 | 必须附实际数量或未评估原因 |
| 整体结论 | 值得进一步核实、存在明确缺口、结论不完整 | 不输出“合规”“可施工”或无条件“适合” |

快速过滤只排除有可信证据证明违反硬条件的房源，例如用户指定的地理范围、租金上限，或经确认的场地边界确实放不下不可替代的最小房间。挂牌面积、估算工位密度和未确认图纸不能单独作为“排不下”的证明。字段缺失进入“资料不足”，不可按零、否或不合格处理。每个排除项都保存规则代码、输入值和解释，允许人工复核。

## 为未来批量计算约定的数据契约

下一阶段先从当前页面状态中抽取纯计算接口，不要求立即上线服务。建议契约如下，正式字段和 JSON Schema 在 ADR-001 的 M1 阶段发布：

```text
evaluate(siteVersion, briefVersion, catalogVersion, rulesVersion, seed)
  -> { candidateLayouts, requirementResults, warnings, computeMetrics }
```

- `siteVersion`：稳定房源 ID、确认版本、毫米坐标的边界、出入口、柱和禁占区；另记录位置、租金等检索元数据及每项资料的来源与可信度。场地几何与挂牌面积分开。
- `briefVersion`：已确认的需求、数量、优先级、允许取舍与仍需澄清的字段。未提及与明确要求零个必须不同。
- `catalogVersion`、`rulesVersion`、`seed`：固定家具尺寸、排布规则与候选生成条件，使同一输入可复现。更换任一版本后，旧评估仍可追溯，但不得当作新版本结论。
- 评估结果：引用上述版本和算法版本，记录每条需求的状态、实际值、要求值、原因、所用候选方案以及生成时间。缓存键由这些输入版本组成，不能只用房源 ID。

当前 `concept()` 等函数依赖全局 `P`，预览使用临时场地上下文计算。扩容前必须去掉这一依赖，让批量任务可以独立、并发地评估房源；不能把临时切换全局项目状态当作服务端接口。

## 分阶段实施路径

| 阶段 | 启动条件 | 实施内容 | 验收门槛 |
| --- | --- | --- | --- |
| 当前 MVP | 仅三个模拟场地 | 保留现有同步生成和并排摘要 | 三个固定样本与 A/B/C、缺口、未评估状态一致；不宣称真实房源适配 |
| 小批量 | 开始录入数十套经核对的场地，或实测发现页面计算影响交互 | 抽取无 DOM、无全局 `P` 的排布内核；在 Web Worker 中批量计算，支持取消、进度和逐批返回 | 现有三个样本结果回归一致；修改需求会使旧结果过期；计算时页面可交互 |
| 房源库 | 房源需要跨设备、多人查询与更新 | 按 ADR-001 的技术路线持久化到 PostgreSQL；为实际使用的地区、租金和面积等检索条件建立索引；记录场地版本与数据质量；先做可信硬条件过滤，再做保守粗评 | 缺失数据不会被误排除；每项排除有可审计理由；场地更新使相关缓存失效 |
| 约一千套 | 已有足够完整的房源数据，且小批量压测证明需要后台计算 | 对全库做快速检索；只对排序靠前的约 20–50 套提交完整排布任务。服务端受控并发、缓存、去重、取消与失败重试；结果逐批显示 | 使用一千套测试数据压测并审查误排除、延迟、任务成本与失败恢复，不依赖浏览器保持打开 |

小批量先用 [Web Worker](https://developer.mozilla.org/docs/Web/API/Web_Workers_API/Using_web_workers) 隔离计算；到房源库阶段再决定后台任务实现，不在 MVP 预装 Redis 或队列服务。PostgreSQL 的索引设计应根据实际查询和执行计划确定，而不是预先建立宽复合索引；参见[官方索引文档](https://www.postgresql.org/docs/current/indexes-multicolumn.html)。

## 一千套房源的请求链路

```text
客户确认需求
  -> 元数据检索与可信硬条件过滤（全部房源）
  -> 资料不足单列，候选房源做保守粗评与排序
  -> 前 20–50 套异步生成完整候选并逐批返回
  -> 用户打开某套房源查看 A/B/C 与逐项证据
```

“前 20–50 套”是初始工程假设，不是产品保证。粗评只能决定计算顺序，不能把未运行完整排布的房源标为“需求已满足”。用户调整需求、场地或家具目录后，依赖旧版本的结果变为过期；任务返回时还要核对版本，不能让晚到的旧结果覆盖新页面。

## 压测和上线判定

在做架构拆分前，先记录当前三个样本以及数十套扩展样本的每阶段耗时、页面长任务、峰值内存与候选生成数量。进入一千套阶段前，准备带已知可行、已知不可行、资料缺失三类标签的测试房源集，并保留三个现有样本作回归。

拟定的工程目标是：一千套检索的首批列表在第 95 百分位请求中于 2 秒内可见；前 20 套完整概念结果在第 95 百分位任务中于 30 秒内返回；计算期间页面仍可操作。它们是待目标硬件和真实数据压测校准的验收目标，不是当前性能实测。上线还必须检查已知可行样本没有被快速过滤错误排除、资料缺失样本仍可见、缓存版本正确、任务失败可重试、结果状态没有夸大。

## 下一次实施从哪里开始

2. 抽取 `makeSimulationProject`、候选生成和 `brokerAssessment` 所需的纯数据接口；先在当前页面调用它，确认结果不变。
3. 再接 Web Worker 和批量进度。只有在真实房源数据、性能样本与多用户需求出现后，才启动 PostgreSQL 检索及服务端任务阶段。
