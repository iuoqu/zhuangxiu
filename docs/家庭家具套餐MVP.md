# 家庭家具套餐 MVP

入口：`home.html`。正式 Vercel 站点的家庭页和脚本受四位 `PIN` 门禁保护：首页可用同一四位码直接进入，直达家庭页则先转到 `home-gate.html`。校验在服务端完成，浏览器只保存有效 8 小时的 HttpOnly 会话 Cookie；不在项目 JSON 中保存门禁码。`HOME_GATE_SECRET` 可用作独立签名密钥；若未配置，则复用已有的服务端 `OPENAI_API_KEY` 签名，缺少签名密钥时门禁关闭访问。AI 生成初稿仍需单独的 `BRIEF_PIN`。本地 `file://` 文件不经过 Vercel 门禁；四位共享码仅适合受邀试用，不应作为真实客户图纸的长期账户权限方案。旧的独立预览部署不会因新部署而自动撤销。

办公工具的欢迎页和顶部导航也提供家庭入口。两个场景分别保存项目；家庭项目导出文件带 `projectType: "home"`，办公项目带 `projectType: "office"`。当前全模拟 MVP 主流程是选虚构户型图和套餐、一键填入模拟家具、调整占位并导出平面初稿；上传客户图片及服务端 AI 识别是独立的可选入口，不属于全模拟演示。第 4 步商品明细默认收起。

## 当前套餐

| 套餐 | 户型 | 商品预算上限 | 必选实物数 |
| --- | --- | ---: | ---: |
| 基础款 | Studio（开放式）、一室一厅（1B1B）或一室一厅＋夹层（Loft） | USD 600 | 11 |
| 舒适款 | 两室两卫（2B2B） | USD 1,200 | 19 |
| 高端款 | 两室两卫（2B2B） | USD 2,000 | 22 |

清单在 `src/domain/home-packages.js` 中逐项定义。2B2B 的床头柜按原需求为整套 2 个；书桌＋办公椅按 1 套、2 件实物计算，价格按套录入。Studio、独立一室一厅与带夹层的一室一厅共用基础款商品清单，但保留不同的户型类型；夹层不自动增加第二套卧室家具。

页面的模拟户型图库提供 Studio、1B1B、Loft、2B2B 四张系统生成的虚构图。选图会同步上方户型与可选套餐；点击“用所选户型生成模拟家具初稿”后，页面创建对应的预设房间、载入 `DEMO-` 商品并绘制逐件家具俯视占位。此路径在 `file://` 下也能运行，不上传图纸、不调用 AI；刷新后保留，项目 JSON 和带水印 PNG 可导出。顶部“快速演示”快捷入口仍可使用。若该户型已有上传图纸，图库不会覆盖它，须先导出备份并主动移除。所有示意尺寸和商品均为虚构，不能证明实际适配。

其他上传入口中，JPG、PNG、WebP 在浏览器内压缩并保存，客户可点击生成待复核初稿；内部仍可在图上选取两点、输入两点间实测毫米数校准比例，再拖出客厅、餐厅、卧室、卫生间、厨房、夹层、挑空、楼梯、露台、储物矩形示意区域。校准后框选的可摆家具房间会得到按像素比例估算的长宽，标为“比例估算”；图上已有文字尺寸则优先保留，二者均需复核。手工框选面积只是概念估计，不代表墙体或净使用面积。PDF 小于 1.5 MB 时保存原图并预览，当前不能在 PDF 上标注。每个户型类型保留自己的图纸，同一 2B2B 图纸在舒适款和高端款之间共享。图纸与标注随家庭项目 JSON 导出、导入。

`scripts/create-loft-plan-project.cjs` 可以把用户提供的 1280×875 主层＋夹层 JPG 生成可导入的本地项目 JSON。输出默认放在不进入 Git 的 `local-projects/`。示意框包含主层客厅、卧室、厨房、餐厅、卫生间、楼梯、露台，以及上层夹层、挑空、楼梯和储物。图上可读的三处尺寸按原文保存：客厅 12′0″×12′10″、卧室 11′0″×14′0″、夹层 10′10″×11′0″；毫米值为英尺英寸换算的整数近似值。未设图纸比例，其他区域也未补造尺寸；正式摆放前还需核实家具外廓、净门宽和楼梯运输路线。夹层没有自动算成第二卧室。

### 客户给图 → 家具平面初稿

客户上传 JPG、PNG 或 WebP 后，先点击“识别户型”：`api/read-home-plan.js` 只读取整图的层数、卧室、客厅、卫生间、夹层和图上文字依据，不画房间框或家具。上传本身不调用 AI；两次识别都要求 `BRIEF_PIN`。模型不确定的数量保持空白，用户必须对照原图补齐或修正并确认。与所选套餐类型不符时，页面提示改选匹配套餐；仍要按原套餐继续则必须明确勾选已核对的例外。户型概况及确认状态随项目 JSON 保存，修改或重新识别会暂停家具预览。

只有确认整体户型后，页面才允许调用 `api/suggest-home-zones.js` 提议房间区域；快捷入口还会检查候选卧室、客厅、夹层数量是否与已确认概况一致，不一致时不覆盖原标注。视觉模型须为客厅、餐厅、卧室和夹层抄出图上房间文字及其位置；服务端会拒绝文字与区域类型不符、文字中心不在候选框内或无可读文字的可摆家具区域。无可读文字的挑空与露台、覆盖过大的固定区域也会被拒绝。返回的区域仍只是**未复核草稿**，自动装入套餐的模拟 SKU（已有商品资料不覆盖），但**不会立即绘制家具**。内部人员必须先逐区核对全部候选区域的名称与边界，之后才会触发逐件家具俯视占位。楼梯、挑空、露台、厨卫和储物区域不分配套餐家具。仅在房间核对后，页面才开放带“初稿、不可直接采购安装”水印的 PNG；项目 JSON 可随时导出。PDF 目前只支持保存预览，不支持自动填家具。

AI 读到的尺寸标为 `ai_draft_printed`，房间标注标为 `reviewStatus: "draft"`，不自动确认。没有印刷尺寸的房间仅生成 `visualSizeMm` 绘图单位，使餐厅等区域在核对后也能看到家具示意；它**不是房间实测或推定尺寸**，不会写入 `dimensionsMm`，尺寸初筛会将其列为待补。自动框可在原图上拖动或缩放，也可在区域列表直接改类型；改类型会清除原 AI 文字、尺寸及家具位置依据，并恢复待核对。内部需按原图逐个核对房间名称与边界，才能生成框内家具并做本地位置标记。框及其复核状态随项目导入导出保留，修改或撤销框复核会清除家具位置标记。现阶段的 PNG 是可讨论的平面初稿，并非根据真实商品及净空审核的可采购安装方案。浏览器以 `file://` 打开时无法调用服务端 AI，应使用部署的验收页或本机 HTTP 服务。

人工校对或导入的区域若缺印刷尺寸、而同图其他可摆区域有尺寸，系统会借用同图的绘图比例生成 `visualSizeMm`，让缺尺寸的餐厅等仍能显示家具占位。该值只用于绘图，不补写 `dimensionsMm`，不能作为房间净尺寸或适配依据；若同图没有可参考尺寸，仍保持待补。

已在一张用户提供的主层＋夹层图纸上做过旧版真实接口试验：未经人工修正的单次输出只有 2/11 个区域达到同类框 IoU≥0.4，按两层裁图分别识别反而只有 1/11。样本太少，不能当作总体准确率；但足以说明旧版“10/10 件绘出”只是示意占位数量，不能证明落位正确。现在整体识别和区域提议虽分成两次视觉调用，但整体识别的文字证据仍是模型自述，不是独立 OCR；区域调用的房间文字锚点也来自该次视觉模型，并不能证明边界正确。当前仍无上线的独立 OCR 与墙体边界核验，也未以真实接口验证新流程的识别准确率，不能直接交付。

### 可选：AI 读取图上印刷尺寸

家庭页在套餐核对区持续标出真实户型与适配证据状态。确认整体户型后，内部也可主动点击“AI 提议房间区域”：只有这次点击才将**整张压缩后的图纸**再次发送到服务端视觉接口。返回的房间框以蓝色虚线叠在原图上，图示尺寸只作为草稿；可在图上拖框内移动、拖四角缩放，也可用列表修改房间类型、毫米尺寸和边界像素。修改边界、类型或数字会取消旧的尺寸确认；在这个人工复核入口中，勾选区域和尺寸、点击应用后才写入项目。错误的建议可不勾选；快捷入口生成后已应用的 AI 框可继续在图上拖动或缩放，也可删除后手工重画。PDF 目前仍只能预览，不能用此功能自动标注；AI 建议不能代表墙体测量、现场净尺寸或家具适配。

区域提议与下方局部尺寸读取都要求服务端 `BRIEF_PIN` 与 `OPENAI_API_KEY`，访问码不写入项目 JSON。区域提议接口是 `api/suggest-home-zones.js`，会校验图片大小、归一化坐标、房间类型和可摆家具区域的图上文字锚点，并只返回最多 20 个候选。服务端调用视觉模型时使用结构化输出；人工复核入口可把勾选建议保存为待复核草稿，快捷入口也只保存草稿，全部区域逐项核对前不绘制家具。直接以 `file://` 打开页面时仍可用演示和手工录入，但不能调用 AI 接口。

上传图片并框好房间后，“AI 读取图示尺寸”会只截取缺尺寸或仅有比例估算的客厅、餐厅、卧室、夹层局部图；只有点击按钮才发送到服务端。服务端用视觉模型读取图中**明确印出的两边尺寸文字**，返回文字证据和毫米换算候选。没有完整标注时返回空值，不从像素或家具猜尺寸。候选仅留在页面临时草稿中；用户对照裁图逐项核对并点“确认并应用”后才写入房间、更新家具预览。修改过的候选记为人工尺寸；项目 JSON 保留确认来源与证据。即使确认，家具摆放也只是概念预览，仍需现场净尺寸核查。

此功能需要服务端，直接双击打开的 `file://` 页面不能调用 API。若已在 `file://` 页面录入资料，先导出家庭项目 JSON，再从**已部署此功能**的 Vercel 站点 `/home.html` 打开并导入 JSON；页面与 `/api/extract-plan-dimensions` 必须在同一个站点。Vercel 部署环境需要 `OPENAI_API_KEY` 和 `BRIEF_PIN`；旧渲染页使用的 `PIN` 与这里的 `BRIEF_PIN` 不是同一个变量，不能只凭 `PIN` 推断新接口可用。新文件必须随部署发布，环境变量的新增或变更也需要新部署才生效。

如需只在本机试验，在 PowerShell 中进入项目目录，设置当前终端的 `BRIEF_PIN`（自定访问码）和 `OPENAI_API_KEY`，运行 `npm run build:home`、`npm run dev:home`，打开 `http://127.0.0.1:8765/home.html` 并导入 JSON。访问码只在本次请求中提交；API 密钥只存于服务端环境变量，不填进网页。本机服务仅监听 `127.0.0.1`。未配置密钥时，其他模拟家具功能照常可用，但 AI 读取按钮会明确报配置缺失。测试只模拟模型响应，没有用真实密钥测试视觉准确率。

用户可以先只填每个必选行的美元单价，立刻看到行小计；所有单价填齐后显示整套价格与预算差额，但明确标为“草算”，不当成正式报价。商品名称可稍后补，SKU 与价格来源默认折叠，在采购核对时展开填写。只有名称、SKU、来源、单价全部齐全，严格的 `budgetStatus` 才可判定；否则正式总价仍为空。数量固定来自套餐。切换套餐时各自已填商品保存在浏览器；可以导出或重新导入家庭项目 JSON，以及导出同时包含草算与严格核对状态的清单审查 JSON。

`src/domain/home-mock-catalog.js` 提供 31 条虚构 SKU，覆盖三个套餐的所有必选行：基础款 9 条，舒适款 11 条，高端款 11 条。每条都以 `DEMO-` 开头，带演示名称、美元单价和可分件时的示意尺寸。用户可展开“查看全部模拟 SKU 库”，也可按“载入本套餐模拟 SKU”填入当前套餐；若当前商品已有内容，替换前会确认，户型图和其他套餐不受影响。三个演示整套金额分别为 $565、$1,085、$1,995，都是人为编造的测试数值，不代表市场可购性。模拟条目带 `simulated: true`，即使字段齐全，严格的采购预算状态仍保持 `pending`、正式总价仍为空；只提供价格草算。

页面顶部有随当前资料变化的主操作入口。生成后自动定位到原户型图上的家具，并把 PNG 下载入口放在图旁；第 4 步商品明细默认收起，可按需查看或修改。第 3 步调用 `src/domain/home-concept-layout.js`：将每行商品展开为逐件占位，默认按套餐房间匹配客厅、餐厅、卧室，也允许逐件改选夹层等已标注区域。商品外廓存在且房间有图示、校准尺寸或仅供绘图的 `visualSizeMm` 时，在原图上绘制带简笔家具纹理的蓝色俯视占位，并提供可切换房间的放大预览；F1、F2 等编号对应下方清单。客厅优先画出电视柜—茶几—沙发的相对关系，卧室优先画出床、两侧床头柜和斗柜，再用无重叠矩形位置补充其他件。没有可靠房间长宽的占位仅供视觉讨论，尺寸初筛仍列为待核对。床垫与床架共用占位，先核对两者示意尺寸，不重复算成地面家具；缺尺寸的套装保持待核对。预览开关与房间指定随项目保存和导出，内容变更时重新计算。模拟 SKU 没有实物照片，蓝色图形不是商品实物图。

第 3 步同时调用 `src/domain/home-fit-screen.js` 做**矩形外廓初筛**：逐件检查房间和商品是否有长宽、外廓是否可沿房间两个直角方向进入、当前占位是否越界或重叠，并核对床垫与床架数量及外廓。若仅旋转 90° 才可能放入，会提示当前预览不自动旋转；简单排布没找到位置时只记为待调整，不能断言放不下。结果分为 `conflict`（已知尺寸的外廓冲突）、`incomplete`（资料或排布不足）和 `outline_clear`（现有矩形无冲突），**所有情况的 `fitStatus` 均为 `not_checked`**。页面逐项给出待补事项，导出清单附 `outlineScreen` 供复核；不会把“矩形无冲突”表述为家具实际适配通过。第 4 步展开采购详情后可修正商品外廓两边毫米数，初筛会随之重算；模拟 SKU 即使改尺寸仍标为模拟。当前不检查门窗和开门轨迹、墙体净边界、固定设备、通行与使用净空、入户门/楼梯搬运路径、现场净尺寸或真实 SKU 规格，不能用于采购或安装承诺。

真实价格由录入者提供，目前没有已接入的真实供应商目录。预算只计算商品及床垫，不含税、配送和安装；结果是商品核对草单，不是正式报价。户型图的比例只取一段人工输入的尺寸，需与原图或现场复核。模拟库虽有示意尺寸，但当前只有矩形外廓初筛，没有逐件真实摆放验证，摆放适配状态始终是 `not_checked`。家庭套餐不调用办公工位、会议室和紧急出口生成规则。

### 本地交付前复核闸门

第 3 步的“交付前复核”由 `src/domain/home-review-gate.js` 生成逐项状态：未放置、先核对 AI 房间框、占位冲突、缺尺寸、待确认图上位置、图上位置已确认。床垫与床架共用占位；书桌＋办公椅等套装仍须分件核对。AI 房间框未经人工核对时，框内家具不能标记为已确认位置；核对房间名称与边界后，才可对具备房间和商品外廓、且当前未冲突的占位做**本地位置标记**。该标记随项目 JSON 保存和导入，绑定当前图纸、房间边界和尺寸、商品身份及外廓、家具位置；依据改变后，旧标记不再生效。导出复核清单包含 `deliveryGate` 的状态和阻断原因。此标记没有审核人身份或服务端审计，不能用来批准交付。由于仍有模拟 SKU、AI 草稿房间、门窗与通道等未核验条件，`canDeliver` 固定为 `false`，页面仅开放带初稿水印的 PNG；正式客户交付流程尚未实现。

`home.html` 使用仓库内的 `home.bundle.js`，除 AI 功能外可直接以本地文件打开。修改 `home.js` 或 `src/domain/home-*.js` 后运行 `npm run build:home` 更新该文件。验证：`npm run test:unit`；安装 Playwright 和 Edge 的环境可运行 `node home.browser.test.cjs`。

### 真实图纸的离线验收（开发用）

`scripts/evaluate-home-plan.mjs` 将一份人工标注项目与**同一张图片、未经人工修正的 AI 区域输出**比较，不发起网络请求。它检查房间及固定区类别、矩形示意框的交并比（IoU）、图上明确印出的尺寸，以及模拟套餐家具占位覆盖率。示意框不是墙体测量，因此区域得分不能证明真实净空或搬运可行。

先让有权使用图纸的人员在已配置的验收站点主动点击“生成家具初稿”，导出原始草稿 JSON；如果使用接口原始响应，也可保存含 `suggestions` 数组的 JSON。使用同一张图纸对应的人工标注项目作基准，在本机运行：

```powershell
node scripts/evaluate-home-plan.mjs --reference "<人工标注项目.json>" --actual "<未经修正的AI草稿.json>" --strict
```

`--strict` 在该样本未过检查时返回退出码 2。输出中的 `samplePass` 只代表这一份图纸是否达到当前诊断门槛；`releaseReady` 固定为 `false`。不同图纸的识别质量、门窗/净空、真实 SKU、审核身份等还需要独立验收。不能用已修正的导出文件冒充 AI 原始表现，也不能把人工标注与其自身对比的满分当作 AI 准确率。

目前本地人工标注样本与自身对照仅用于检查评测器：11/11 个示意区和 3/3 组印刷尺寸匹配，但自动占位只覆盖 7/10 件（70%）。未放置的是餐桌和两把餐椅：人工标注的餐厅没有实测尺寸或绘图单位；AI 草稿入口会为无印刷尺寸的可摆家具区另建仅供预览的 `visualSizeMm`。这个结果不是一次真实模型测试，也不能靠编造餐厅实际尺寸消除阻断。本次没有再次把客户原图发送至外部 AI。

### 独立文字锚点诊断（尚未接入客户页面）

`scripts/evaluate-home-zone-anchors.mjs` 在本机用 Tesseract.js 读取图上的英文房间文字及坐标，再与 AI 候选框交叉检查。首次运行需下载英文 OCR 语言数据，但图纸留在本机；输出不包含图片。运行：

```powershell
node scripts/evaluate-home-zone-anchors.mjs --reference "<人工标注项目.json>" --actual "<未经修正的AI响应.json>"
```

诊断将候选框区分为：同类文字在框内、框内混有其他房间文字、同类文字在框外、框内是其他房间文字、未读到相关文字。对当前唯一的用户图纸，整图 AI 的 10 个候选框中有 2 个得到同类文字支持、5 个需重点复核、3 个无文字证据；2 个有文字支持的框恰好也是 IoU≥0.4 的框。按楼层裁图的另一组输出中，有 2 个框得到文字支持，但其中 1 个边界仍不达标。因此文字位置只是一道**候选框筛查**，不是边界、尺寸或家具适配证明。简单沿矩形四边统计黑色墙线也不能充当通用判据：人工示意框常不沿墙线。未在多样本上验证前，不将这些诊断结果自动转为“已确认”或交付放行。
