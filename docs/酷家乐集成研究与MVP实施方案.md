# 酷家乐集成研究与 MVP 实施方案

更新时间：2026-09-29

适用项目：AI 办公空间设计工具

文档目的：确定自研产品与酷家乐的职责边界、户型输入方式、API 接入链路、人工确认流程和 MVP 实施顺序。

## 1. 结论

MVP 不应复制一个完整的酷家乐。我们的产品负责获客入口、英文交互、办公需求采集、A/B/C 初稿生成、办公规范检查、家具清单、报价与客户流程；酷家乐负责重资产能力，包括复杂图纸识别、成熟的墙门窗编辑、精细 2D/3D 设计和后续渲染。

推荐采用“自研前台 + 酷家乐能力层”的混合方案：

1. 简单矩形、多边形和用户手工输入由我们直接生成标准场地数据。
2. DWG 交给酷家乐 CAD 识别；JPG、PNG 和扫描 PDF 交给临摹图识别。
3. 所有来源都转换成我们自己的统一场地 Schema，不能让业务数据只存在酷家乐中。
4. 识别完成后必须经过用户核对。酷家乐任务成功只代表算法执行完成，不代表户型正确。
5. 用户确认后，我们生成办公布局初稿和检查结果；选中的方案再进入酷家乐做精细编辑和渲染。
6. 酷家乐的 `planId` 是外部资源标识，不是本系统项目主键。项目、版本、确认状态和商业数据都由我们保存。

## 2. 产品边界

### 2.1 我们负责的能力

- 英文优先的项目创建和需求问卷。
- 场地尺寸、形状、门窗、柱体、固定区、入口和安全出口的轻量编辑。
- 开放式、格子间、独立办公室和混合模式的选择。
- 工位数、会议室、功能区、预算和家具偏好的采集。
- 自动生成两到三版办公初稿，并解释每版取舍。
- 工位容量、家具碰撞、通道占用、门扇冲突、出口遮挡和路线连续性检查。
- 家具清单、报价、项目保存、只读分享和线索转化。
- 用户对识别结果的确认状态、版本记录和审计信息。
- 酷家乐 API 的封装、重试、费用控制和供应商替换适配层。

### 2.2 酷家乐负责的能力

- CAD 和临摹图识别。
- 成熟的墙、门窗、柱体、房间等户型编辑能力。
- 精细 2D/3D 设计器及其视角、材质、模型与渲染能力。
- 方案、户型和渲染结果的云端管理。
- 在已购买权限范围内提供设计工具嵌入、单点登录、工具小程序和事件监听。
- 后期生成效果图、全景图、施工图或酷家乐侧清单时提供基础平台能力。

### 2.3 不应依赖酷家乐直接完成的能力

- 办公行业专用的需求问卷和销售漏斗。
- 面向项目目标的 A/B/C 布局评分，例如工位数、会议配套、采光、通道和预算之间的权衡。
- 本项目定义的逃生路线连续性、门前净空和家具占用通道检查。
- 我们的家具 SKU、价格、采购、安装、佣金和客户订单流程。
- 完全白标的英文用户体验。酷家乐编辑器是否提供英文界面取决于购买版本、Coohom 权限和合同配置。
- “识别正确”的业务确认。该状态应由我们记录。

## 3. 用户工作流

### 3.1 首次进入

用户首先看到清晰的三步目标，而不是一个空白 CAD 画布：

1. 建立或上传场地。
2. 填写办公需求并生成初稿。
3. 选择方案，检查并进入精细设计。

首页主操作应为 `Create a project`，同时提供示例项目。新项目中先询问用户已有资料：

- 只有长宽尺寸；
- 可以手绘轮廓；
- 有 DWG；
- 有 PDF；
- 有 JPG 或 PNG；
- 暂时没有图纸，先用模板。

### 3.2 建立场地

系统根据输入类型自动选择路径，但对用户统一显示为：

```text
上传或绘制
→ 自动识别
→ 核对尺寸和固定结构
→ Confirm floor plan
```

核对时只要求确认影响办公布局的内容：

- 总长度、总宽度和比例；
- 外轮廓是否闭合；
- 门窗位置与开门方向；
- 柱体、核心筒和不可占用区；
- 主要入口和安全出口；
- 需要保留的隔墙。

### 3.3 生成办公初稿

用户填写工位数、办公模式、会议席位、独立办公室、前台、茶水、文件柜等需求。系统先生成 A/B/C 三版可解释初稿：

- A：平衡方案；
- B：容量优先；
- C：舒适度或独立办公室优先。

每版必须同时显示工位数量、会议席位、功能区数量、通道检查、主要风险和预计家具费用。用户在这一步不需要学习酷家乐。

### 3.4 精细设计

用户选择一版后，可进入酷家乐编辑器做墙体、门窗、模型、材质和效果图的精细修改。返回本系统后，系统继续管理报价、清单、分享、订单和方案版本。

## 4. 输入文件与处理策略

| 输入类型 | MVP 处理方式 | 是否需要酷家乐识别 | 必须人工确认的内容 |
|---|---|---:|---|
| 长宽尺寸 | 我们生成矩形或 L 形场地 | 否 | 单位、总尺寸、入口位置 |
| 手工多边形 | 我们的轻量 2D 编辑器 | 否 | 闭合轮廓、比例和墙厚 |
| 我们已生成的结构化场地 | 转换为酷家乐 FPI 并导入 | 否 | 导入后结构一致性 |
| 单户型 DWG | 酷家乐 CAD 识别生成 FPI | 是 | 单位、图框、墙门窗和柱体 |
| 一个 DWG 含多个图框 | 先 CAD 分图，再识别指定区域 | 是 | 选择正确图框和楼层 |
| DXF | 优先由上传服务转换为 DWG；合同确认后再决定是否直传 | 可能 | 单位和转换结果 |
| JPG/PNG | 临摹图识别 | 是 | 标尺、透视畸变、门窗和墙厚 |
| 扫描 PDF | 每页转图片后进入临摹流程 | 是 | 页码、比例和识别结果 |
| 矢量 PDF | 可转 DWG 或高分辨率图片，按质量选择路径 | 可能 | 转换后的比例和图层 |
| 低清、手绘或异形图 | 图片作底图，用户半自动描线 | 可选 | 全部关键结构 |

当前公开文档中的 CAD FPI 接口明确写明 `cad_file` 支持公共网络可访问、以小写 `.dwg` 结尾的地址。因此不能在未得到酷家乐书面确认前承诺 DXF 或 PDF 可以直接调用该接口。

## 5. 统一数据模型

我们的内部数据模型是供应商中立的事实来源。建议至少保存以下对象：

```json
{
  "schemaVersion": "office-site/v1",
  "projectId": "prj_123",
  "unit": "mm",
  "levels": [
    {
      "levelIndex": 1,
      "height": 2800,
      "boundary": [],
      "walls": [],
      "openings": [],
      "columns": [],
      "fixedZones": [],
      "entrances": [],
      "emergencyExits": [],
      "noPlacementZones": []
    }
  ],
  "source": {
    "type": "dwg",
    "fileId": "file_123",
    "recognitionProvider": "kujiale"
  },
  "externalRefs": {
    "kujialePlanId": null,
    "kujialeDesignId": null
  }
}
```

内部字段与酷家乐 FPI 的主要映射为：

| 内部对象 | 酷家乐对象 | 说明 |
|---|---|---|
| `walls` | `walls` | 起终点、厚度、高度、直线或弧线 |
| `openings` | `holes` | 门窗类型、起终点、开门侧、高度和窗台高度 |
| `rooms` | `rooms` | 房间名称和内部定位点 |
| `columns` | `pillars` | 多边形轮廓和类型 |
| `beams` | `beams` | 起终点、高度和厚度 |
| 设备井或烟道 | `flues` | 多边形和外部标识 |

安全出口、通道、禁占区、办公功能需求和检查结果不应硬塞进酷家乐户型 Schema；这些是我们的业务对象。

## 6. 已确认的酷家乐 API 能力

### 6.1 结构化户型导入

```http
POST https://openapi.kujiale.com/v2/floorplan/import/for/partner
```

Query 参数：

- `appuid`：必填，映射第三方用户；
- `plan_id`：选填，传入时更新属于当前账号体系的户型。

Request Body 支持 `walls`、`holes`、`rooms`、`pillars`、`flues`、`beams` 等结构。成功时 `c` 为 `0`，`d` 返回酷家乐户型 ID。

该接口是我们自行绘制或自动生成场地时的首选路径。它比“创建空白方案后用插件逐个画墙”更直接；只有购买权限不包含该接口时，才退回空白方案加工具小程序写入的方案。

### 6.2 CAD 识别生成 FPI

```http
POST https://openapi.kujiale.com/v2/fpi-from-cad/import/async
```

已确认参数：

- `appuid`：必填；
- `cad_file`：必填，可从公网直接访问且以小写 `.dwg` 结尾；
- `model_version`：选填，文档列出版本 1、2，默认 2；
- `unit`：选填，1 英寸、2 英尺、4 毫米、6 米，默认毫米；
- `cadSplitRegion`：选填，限制识别图纸中的包围盒。

接口返回 `taskId`，随后调用“CAD 导入生成 FPI 轮询结果”接口取得结构化结果。轮询接口的具体 URL 和返回字段应以实际购买账号内的最新文档为准，不在代码中凭经验猜测。

### 6.3 CAD 分图

```http
POST https://openapi.kujiale.com/v2/cad-split/async
```

当一个 CAD 文件中包含多个户型图框时，该接口先识别各图框范围。调用方负责让用户选择正确的区域和楼层，再把区域传给 CAD FPI 识别任务。

### 6.4 临摹图导入

酷家乐文档中提供临摹图导入方案、临摹图生成 FPI、图片分图及对应轮询能力。已经确认的方案轮询接口之一为：

```http
GET https://openapi.kujiale.com/v2/bitmap/floorplan-import/status
```

成功结果包含 `planId` 和 `levelId`。图片自动识别比例可能失败，因此 UI 必须提供一条已知尺寸供用户校准。

### 6.5 户型生成装修方案

```http
POST https://openapi.kujiale.com/v2/floorplan/lib/async
```

该接口需要已有 `plan_id`，用于把户型库户型复制或转换为可装修设计方案，并返回异步任务 ID。它不是“从我们的 JSON 创建户型”的接口，不能替代结构化户型导入。

### 6.6 读取最终结构

```http
GET https://openapi.kujiale.com/v2/floorplan/structure/detail/data
```

通过 `planId` 获取各层房间、墙体等结构数据。用户从酷家乐编辑器保存后，我们应再次读取并转换回内部 Schema，形成确认版本。

## 7. 识别与确认状态机

识别状态和几何确认状态必须分开：

```text
upload_status
pending → uploading → uploaded → failed

recognition_status
not_started → queued → processing → succeeded → failed

geometry_status
unreviewed → needs_review → editing → confirmed → superseded

sync_status
not_synced → importing → synced → changed_in_kujiale → read_back → failed
```

建议保存以下标识：

- `projectId`：我们的项目 ID；
- `siteVersionId`：每次确认后的场地版本；
- `sourceFileId`：原文件；
- `recognitionTaskId`：酷家乐异步任务；
- `kujialePlanId`：户型 ID；
- `kujialeDesignId`：装修方案 ID；
- `levelId`：楼层 ID；
- `geometryHash`：确认版本的结构摘要；
- `confirmedBy`、`confirmedAt`：人工确认审计字段。

截至本文更新时间，公开文档中没有发现一个可以代表“客户确认户型正确”的统一确认 API。我们的 `Confirm floor plan` 按钮应完成以下动作：

1. 确认当前识别任务成功；
2. 从酷家乐读取最新结构；
3. 转换为内部 Schema；
4. 运行基础几何校验；
5. 保存新 `siteVersionId` 和 `geometryHash`；
6. 把 `geometry_status` 改为 `confirmed`；
7. 解锁 A/B/C 布局生成。

## 8. 自动校验与人工核对

### 8.1 自动校验

- 坐标和尺寸为有效数值；
- 单位明确且转换一致；
- 墙线没有异常短线或大量重复线；
- 外轮廓可以组成闭合区域；
- 房间定位点位于有效区域；
- 门窗落在墙线上；
- 柱体和固定区位于场地范围内；
- 总面积与用户输入或图纸标注的面积差异在项目阈值内；
- 导入前后墙数、门窗数和包围盒没有明显变化。

### 8.2 人工核对

- 图纸比例；
- 选中的 CAD 图框和楼层；
- 外墙与需要保留的隔墙；
- 门窗位置和开门方向；
- 柱体、核心筒、设备井；
- 主入口、安全出口和不可占用区；
- 对办公布局有影响的异形边界。

UI 应把这一步命名为 `Review detected floor plan`，不要展示“任务成功”就直接进入家具布局。

## 9. 系统架构

```text
Web 前端
  ├─ 项目与需求问卷
  ├─ 轻量 2D 场地编辑器
  ├─ A/B/C 初稿与检查结果
  └─ 酷家乐编辑器入口
          │
Vercel API / 后端服务
  ├─ 上传签名
  ├─ 酷家乐鉴权与 API 适配器
  ├─ 异步任务轮询与重试
  ├─ FPI 转换器
  ├─ 结构回读与版本确认
  └─ 成本、限流和审计日志
          │
对象存储 + 数据库
          │
酷家乐 OpenAPI / 设计工具 / 工具小程序
```

关键实现约束：

- `appKey`、`appSecret`、Access Token 只能存在服务端；不得写入 `studio.js` 或浏览器 LocalStorage。
- 上传文件先进入对象存储，再向酷家乐提供有时效、可访问的 URL。
- 异步任务必须有退避轮询、超时、失败重试和幂等键。
- 不让浏览器直接轮询酷家乐；浏览器只轮询我们的任务 API。
- 所有外部响应保留原始副本和转换日志，便于处理识别争议。
- 删除项目时要分别处理本地数据、对象存储文件和酷家乐资源，不能只删一个 ID。

建议的内部接口：

```text
POST /api/files/upload-url
POST /api/recognition-tasks
GET  /api/recognition-tasks/:id
POST /api/floorplans/import
GET  /api/floorplans/:projectId/review
POST /api/projects/:projectId/confirm-floorplan
POST /api/projects/:projectId/generate-layouts
POST /api/projects/:projectId/kujiale-design
POST /api/projects/:projectId/sync-from-kujiale
```

## 10. 英文产品方案

英文版可以实现，但应分两层处理：

- 我们控制的页面全部采用英文，并从第一天使用国际化键值，不把文案写死。
- 酷家乐编辑器内部语言取决于购买版本、Coohom 能力和账号配置。合同中必须明确 `en_US`、白标范围、域名、登录流程和可隐藏的原生界面。

如果酷家乐内嵌编辑器无法满足纯英文和白标要求，MVP 可以让客户始终停留在我们的英文流程，只有内部设计师或已付费专业用户进入酷家乐。这样不会让语言问题阻塞前端漏斗。

## 11. 漏斗与收费衔接

推荐把高成本的酷家乐能力放在用户已经表达明确意向之后：

```text
免费获客
建立项目 → 输入需求 → 简单场地 → 一版预览

低价转化
完整 A/B/C 初稿 → 基础通道检查 → PDF/分享

项目服务
复杂图纸识别 → 精细设计 → 酷家乐渲染 → 家具清单与报价

专业订阅
多物业、多方案、团队协作和中介展示
```

复杂 CAD/图片如果必须在最前面识别，可以给每个账户少量免费额度，超出后使用项目点数或付费解锁，避免识别和渲染费用无限暴露。

当前需求文档中的中介价为 `$69/月` 或 `$600/年`，可继续作为验证价格。客户项目费应覆盖识别、方案复制、渲染、存储和人工支持成本，不应在客户账单中单独出现“酷家乐 API 费”。实际价格必须在取得酷家乐书面报价和调用配额后重新测算。

酷家乐公开页面没有提供适用于本项目的统一 API 价目，因此预算中不得使用未经确认的单次调用价格。采购模型可能同时包含企业 SaaS 账号、开放 API 能力包、调用或渲染额度、模型库和技术支持费用。

## 12. MVP 实施顺序

### 阶段 0 采购前技术验证

用一个真实办公室样例完成端到端 Spike：

1. 取得测试 AppKey、AppSecret 和所需接口权限；
2. 上传单户型 DWG；
3. 创建 CAD FPI 任务并轮询成功；
4. 导入结构化户型并取得 `planId`；
5. 打开户型或装修方案编辑器；
6. 修改一面墙和一个门后保存；
7. 通过 API 读回结构；
8. 验证英文界面、SSO、回跳和费用计量。

只有该链路成功后，才签订正式集成排期。

### 阶段 1 自研核心漏斗

- 英文项目创建；
- 尺寸输入和简单多边形；
- 门窗、柱体、入口、安全出口和禁占区；
- 办公需求问卷；
- A/B/C 初稿；
- 检查结果、统计、清单和本地保存。

### 阶段 2 酷家乐户型通道

- 统一 Schema 与 FPI Adapter；
- 合作伙伴户型导入；
- `appuid` 映射；
- `planId`、`designId` 和任务状态存储；
- 结构回读和版本确认。

### 阶段 3 复杂文件识别

- DWG 上传；
- CAD 分图和 FPI 识别；
- JPG/PNG/扫描 PDF 临摹识别；
- 比例校准和 Review UI；
- 失败后切换为半自动描线。

### 阶段 4 精细设计与商业闭环

- 酷家乐编辑器嵌入或安全跳转；
- 保存回调和回跳；
- 选定初稿推入酷家乐；
- 效果图、全景图和只读分享；
- 家具映射、报价、支付和中介来源追踪。

## 13. 验收标准

### 13.1 户型导入

- 自研矩形和 L 形场地可创建酷家乐 `planId`。
- 导入前后主要尺寸误差不超过项目设定阈值。
- 门窗、墙、柱数量和位置可被结构回读验证。
- 重复请求不会生成不可控的重复户型。

### 13.2 CAD 识别

- 公网 DWG 可创建异步任务并显示进度。
- 单位选择错误时允许重新识别。
- 多图框 CAD 可选择识别区域。
- 失败任务显示可理解的英文错误和重试入口。

### 13.3 图片识别

- 支持 JPG、PNG 和 PDF 页图。
- 用户可用一条已知尺寸校准比例。
- 自动比例失败时不会错误地直接进入布局。

### 13.4 确认

- 没有确认的场地不能生成正式 A/B/C 方案。
- 每次确认生成独立 `siteVersionId`。
- 修改酷家乐户型后，系统能检测结构变化并要求重新确认。

## 14. 采购时必须向酷家乐确认的问题

1. 是否开通“合作伙伴户型导入”和多层户型导入；
2. 是否开通 CAD 导入生成 FPI 的创建和轮询接口；
3. 是否开通临摹图生成 FPI 或方案的创建和轮询接口；
4. 支持的 DWG 版本、文件大小、图层限制、并发和日配额；
5. DXF、矢量 PDF、扫描 PDF 是否有原生入口；
6. 对象存储 URL 是否允许签名参数，下载超时是多少；
7. 设计工具如何嵌入、如何 SSO、如何回跳、是否有保存事件；
8. `appuid` 与酷家乐账号如何映射，是否需要为每个终端用户创建账号；
9. 英文界面、Coohom、白标、自定义域名和隐藏菜单的范围；
10. 能否通过工具小程序批量创建或更新墙、柱、门窗和家具；
11. 结构回读接口覆盖哪些对象，修改后多久可读取；
12. 户型、方案、渲染、存储和 API 分别如何计费；
13. 测试与生产是否分环境，是否提供沙箱额度；
14. 数据存储区域、数据导出、删除、备份和服务终止后的迁移方式；
15. API 版本升级、弃用通知、SLA 和技术支持响应时间。

## 15. 风险与回退方案

| 风险 | 影响 | 回退方案 |
|---|---|---|
| 购买套餐不含结构化导入 | 不能直接创建 `planId` | 空白模板方案 + 工具小程序写入；同时保留内部 Schema |
| CAD 接口只支持 DWG | DXF/PDF 不能直传 | 服务端转换，或改走临摹图/人工描线 |
| 图片识别比例错误 | 全部家具尺寸失真 | 强制标尺校准，未确认不得生成正式方案 |
| 酷家乐英文或白标不足 | 客户体验割裂 | 客户停留在自研英文界面，仅内部设计师进入酷家乐 |
| API 费用高或配额低 | 免费用户成本失控 | 免费额度、排队、结果缓存和付费解锁 |
| 供应商锁定 | 后续迁移困难 | 内部 Schema 为主，酷家乐仅通过 Adapter 接入 |
| 异步任务超时 | 用户误以为失败 | 后台任务、断点续查、邮件通知和幂等重试 |
| API 成功但几何错误 | 产生不可用方案 | 人工 Review、自动几何校验和确认版本 |

## 16. 当前决策记录

- 决定：MVP 采用混合架构，不自研完整的专业 2D/3D 编辑器。
- 决定：前一到两步保持自研英文体验，酷家乐不直接成为产品首页。
- 决定：简单结构直接使用合作伙伴户型导入，空白模板加插件只作回退。
- 决定：复杂 DWG 和图片使用酷家乐识别，但必须经过人工确认。
- 决定：我们的统一 Schema、项目版本和业务状态是事实来源。
- 决定：`SUCCESS` 仅代表识别任务完成，不能自动把场地标记为 `confirmed`。
- 待确认：购买套餐、英文白标、SSO、保存回调和各接口的正式配额与价格。
- 待确认：将我们的办公家具 SKU 映射到酷家乐商品模型的具体接口和模型制作流程。
